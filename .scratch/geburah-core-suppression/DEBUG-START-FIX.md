# Geburah 调试启动无响应修复记录

日期：2026-08-17

## 现象

在第一天的新存档执行 Geburah 核心抑制调试命令后，视觉安全警示窗口正常出现；玩家确认后窗口关闭，但核心抑制、Geburah 实体和 Boss Bar 均未出现，聊天栏也没有失败原因。

## 已确认根因

1. `debugStartChallenge` 虽然声明为“跳过准入检查”，但确认结束后的 `beginDebugChallenge` 又调用了遭遇的正式准入检查。玩家不在设施维度时，启动直接返回 `false`。
2. `launchPendingChallenge` 对调试启动失败只负责关闭警示窗口，没有把失败原因发送给玩家，因此表面上像是确认按钮没有生效。
3. 第一天下惩戒部尚未开放。Geburah 原本只允许在 `disciplinary/upper-main` 搜索出生点，调试环境缺少可用惩戒部房间时仍会初始化失败。
4. 从其他维度传送到设施时，旧代码错误地在玩家当前维度检查公司结构是否生成，可能把玩家送到设施维度的 `(0, 4, 0)`，而不是公司入口。

## 修复方案

- 在 `CoreSuppressionEncounter` 增加独立的 `debugStart` 生命周期入口，正式启动和调试启动不再共用准入规则。
- 正式 Geburah 核心抑制继续要求所有在线玩家位于设施维度，并继续只在惩戒部主休息室生成。
- 调试启动允许从第一天的新存档直接执行；启动成功后会把所有在线玩家传送进设施并禁用工作设备。
- 惩戒部未开放或正式出生点不可用时，调试启动会在控制部主休息室附近搜索不碰撞、非玻璃、无液体的安全点。该回退只用于调试模式。
- 修正设施传送的结构生成检查，使其检查设施维度而不是玩家原维度。
- 调试启动任何阶段失败时，聊天栏现在都会显示明确的“调试启动失败”原因。

## 验证

- `compileJava` 通过。
- `processResources` 通过。
- 447 个 JVM 测试通过，0 失败，0 错误。
- `zh_cn.json` 与 `en_us.json` 均通过 JSON 解析。
- 客户端确认窗口到集成服务器的完整交互仍需在重启后的 `runClient` 中进行一次人工回归。
