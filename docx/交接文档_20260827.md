### 3.2 已实现机制

工作完成后：

```text
勇气等级 >= IV
或
自律等级 <= II
→ 员工被机器吞入并死亡
```

坏结果：

```text
逆卡巴拉计数器 -1
```

计数器归零：

```text
下一名尝试开始工作的员工直接被吞入
→ 计数器恢复
```

机器启动：

```text
播放开启动画
→ 演奏 5 秒
→ 选择一个目标进入“机器狂想曲”控制
```

目标优先级：

```text
本部门文职
→ 本部门员工
→ 全设施文职
→ 全设施员工
```

受控者：

- 最大生命值约翻倍并回满；
- 进入 `HostileControlState`；
- 设施视为敌对和不可调度；
- 追击其他员工或文职；
- 施加减速；
- 3 秒攻击前摇；
- RED 伤害公式：

```text
16 + 3 × 勇气等级
```

- 击杀后尝试返回歌唱机；
- 返回后令机器再次演奏并继续扩散。

```text

```

现象：

- 控制状态建立成功；
- 目标 eligibility 检查成功；
- 但 `LivingTickEvent` 驱动攻击没有在合成员工上执行。

高概率原因：

`EmployeeServerPlayer` 由 `EmployeeRuntimeManager` 手动调用 `doTick()`，不一定会经过正常实体 `LivingTickEvent` 调度。与此同时，`EmployeeRuntimeManager` 遇到 `HostileControlState` 后直接停止普通任务并返回，因此歌唱机控制逻辑可能没有执行入口。

建议修复：

1. 将 `SingingMachineControl` 的每 tick 实现提取为公开方法，例如：

```java
SingingMachineControl.tickControlled(entity);
```

2. Forge `LivingTickEvent` 调用该方法，覆盖真人玩家与正常 Mob；
3. `EmployeeRuntimeManager` 的受控分支也显式调用该方法，覆盖 `EmployeeServerPlayer`；
4. 重新添加真实 AI 员工攻击、击杀、回机 GameTest；
5. 验证真人受控玩家的 `PlayerControlLock`。

不要仅延长测试等待时间。此前已尝试关闭无敌、清除无敌帧、预设目标和攻击前摇，仍无法在合成员工夹具中触发攻击。

## 四、完整设施区域查询修复

此前：

```java
FacilityWorldLayout.areaAt(dimension, position)
```

只查询固定布局，不包含 `CompanyRoomData` 中的动态收容单元。因此玩家站在收容室内部时，可能返回空部门。

现在新增：

```java
FacilityWorldLayout.facilityAreaAt(level, position)
```

流程：

```text
固定设施区域
+ 动态收容区域
→ 绑定 departmentId / groupId
→ FacilityAreaSelection 处理重叠
→ 返回完整 FacilityAreaEntry
```

歌唱机已改用该接口。

重叠优先级仍沿用现有规则：

1. 电梯/电梯井；
2. 走廊/休息室；
3. 收容单元；
4. 其他。

所以门口与走廊重叠时识别为走廊；收容室内部能识别为收容单元。

测试：

- `FacilityWorldLayoutTest`
- `FacilityAreaSelectionTest`
- 均通过。

这是一个已确认的可维护性问题：此前固定区域查询和完整区域查询没有明确接口区分，调用者容易误用。后续判断实体所在设施区域时应优先使用 `facilityAreaAt()`。
